# เช็กลิสต์การจัดการสิทธิ์และการเข้าถึงข้อมูลส่วนบุคคล
## สำหรับทีมงานภายในแพลตฟอร์ม ChauatGo

> **สถานะ:** แนวทางปฏิบัติสำหรับนำไปปรับใช้  
> **เวอร์ชัน:** 1.0  
> **วันที่:** [วัน เดือน ปี]  
> **ผู้รับผิดชอบเอกสาร:** [ชื่อ/ตำแหน่ง]

เอกสารนี้ใช้กำหนดแนวทางควบคุมการเข้าถึงข้อมูลลูกค้า ร้านค้า และไรเดอร์ของทีม ChauatGo โดยใช้หลัก **เข้าถึงเท่าที่จำเป็นต่อหน้าที่ (least privilege)** แยกหน้าที่สำคัญออกจากกัน และตรวจสอบย้อนหลังได้

---

## 1. สิ่งที่ต้องกำหนดก่อนเปิดระบบ

- [ ] แต่งตั้งเจ้าของระบบ (System Owner) และผู้รับผิดชอบข้อมูลส่วนบุคคล
- [ ] ทำบัญชีรายการระบบและฐานข้อมูลทั้งหมด เช่น เว็บไซต์ Firebase Firestore Firebase Storage Firebase Auth ระบบแผนที่ ระบบแชท ระบบชำระเงิน ระบบแจ้งเตือน Analytics และ Vercel/GitHub
- [ ] ทำ Data Inventory ว่าระบบใดเก็บข้อมูลประเภทใด และข้อมูลไหลไปยังผู้ให้บริการรายใด
- [ ] จัดชั้นข้อมูลอย่างน้อยเป็น `ทั่วไป`, `ส่วนบุคคล`, `ส่วนบุคคลความเสี่ยงสูง`, และ `ข้อมูลอ่อนไหว`
- [ ] จัดทำ Data Flow Diagram ตั้งแต่การสมัคร การสั่งซื้อ การรับงาน การติดตาม GPS การจ่ายเงิน และการลบบัญชี
- [ ] กำหนดเจ้าของข้อมูลแต่ละระบบและผู้อนุมัติสิทธิ์
- [ ] จัดทำ Access Matrix ระบุว่าแต่ละบทบาท “ดู”, “สร้าง”, “แก้ไข”, “ส่งออก”, “ลบ” หรือ “อนุมัติ” ข้อมูลได้หรือไม่
- [ ] กำหนดรอบทบทวนสิทธิ์ เช่น ทุก 3 เดือน และทบทวนทันทีเมื่อเปลี่ยนตำแหน่งหรือมีเหตุผิดปกติ

---

## 2. บทบาทภายในที่แนะนำ

### 2.1 ผู้ดูแลระบบระดับสูง

- [ ] มีจำนวนจำกัดและระบุรายชื่อชัดเจน
- [ ] ใช้สำหรับกำหนดค่าความปลอดภัยหรือแก้เหตุฉุกเฉินเท่านั้น
- [ ] ไม่ใช้บัญชีระดับสูงในการทำงานประจำวัน
- [ ] ต้องเปิด MFA และมีการบันทึกทุกกิจกรรม
- [ ] การลบข้อมูลจำนวนมาก เปลี่ยน Security Rules หรือเปลี่ยนผู้ดูแล ต้องมีผู้อนุมัติอย่างน้อย 2 คน

### 2.2 ทีมบริการลูกค้า

ควรเห็นเฉพาะข้อมูลที่จำเป็นต่อการช่วยเหลือ เช่น ชื่อที่ใช้ติดต่อ เลขคำสั่งซื้อ สถานะงาน และช่องทางติดต่อที่ระบบจัดให้

- [ ] ปกปิดเลขบัตรประชาชน บัญชีธนาคาร และข้อมูลลับอื่น
- [ ] จำกัดการดู GPS ให้เห็นเฉพาะงานที่กำลังให้บริการหรือข้อร้องเรียนที่ได้รับมอบหมาย
- [ ] ไม่ให้ส่งออกฐานข้อมูลทั้งหมด
- [ ] การดูหรือดาวน์โหลดรูปพัสดุและเอกสารต้องมีเหตุผลหรือ Ticket อ้างอิง
- [ ] บันทึกผู้ดูข้อมูล เหตุผล และเวลาที่เข้าถึงข้อมูลความเสี่ยงสูง

### 2.3 ทีมปฏิบัติการร้านค้าและไรเดอร์

- [ ] เห็นเฉพาะข้อมูลที่เกี่ยวข้องกับงานที่รับผิดชอบ
- [ ] เห็นสถานะบัญชีและเอกสารเฉพาะส่วนที่จำเป็นต่อการตรวจสอบ
- [ ] ไม่เห็นรหัสผ่านหรือ Token ของผู้ใช้
- [ ] ไม่เห็นข้อมูล GPS ย้อนหลังทั้งหมดโดยอัตโนมัติ
- [ ] ต้องมีขั้นตอนขอสิทธิ์ชั่วคราวสำหรับกรณีตรวจสอบข้อพิพาท

### 2.4 ทีมการเงินและบัญชี

- [ ] เข้าถึงข้อมูลยอดเงิน รายการชำระเงิน และข้อมูลภาษีเท่าที่จำเป็น
- [ ] ไม่เห็นเนื้อหาแชทหรือ GPS หากไม่เกี่ยวข้องกับงานบัญชี
- [ ] ปกปิดเลขบัญชีหรือข้อมูลการเงินในหน้าจอและไฟล์ส่งออก
- [ ] การส่งออกข้อมูลการจ่ายเงินต้องมีผู้อนุมัติและมีวันหมดอายุของไฟล์

### 2.5 ทีมพัฒนาและวิศวกรรม

- [ ] ใช้ข้อมูลจำลองหรือข้อมูลนิรนามใน Development และ Staging
- [ ] ห้ามคัดลอก Production Database ลงเครื่องส่วนตัว
- [ ] ห้ามใส่ข้อมูลส่วนบุคคลจริงใน Source Code, Git Commit, Issue, Log หรือ Screenshot
- [ ] แยก Project/Database/Key ของ Development, Staging และ Production
- [ ] ใช้ Service Account แยกตามบริการและให้สิทธิ์เฉพาะ Resource ที่ต้องใช้
- [ ] การเข้าถึง Production ต้องมีเหตุผล Ticket และบันทึกการดำเนินการ

### 2.6 ฝ่ายบริหารหรือเจ้าของกิจการ

- [ ] ใช้ Dashboard หรือรายงานรวมที่ไม่เปิดเผยข้อมูลรายบุคคลเกินจำเป็น
- [ ] หากจำเป็นต้องดูข้อมูลรายคน ต้องมีวัตถุประสงค์และบันทึกการเข้าถึง
- [ ] ไม่ใช้บัญชีร่วมกัน แม้เป็นผู้บริหาร

---

## 3. ข้อมูลที่ต้องจำกัดเป็นพิเศษ

- [ ] GPS แบบละเอียดของไรเดอร์และลูกค้า
- [ ] ที่อยู่บ้าน จุดรับส่ง และเส้นทางย้อนหลัง
- [ ] เบอร์โทรศัพท์และข้อมูลติดต่อส่วนตัว
- [ ] บัตรประชาชน ใบขับขี่ เอกสารสมัครไรเดอร์ และเอกสารร้านค้า
- [ ] ข้อมูลบัญชีธนาคารและข้อมูลภาษี
- [ ] รูปพัสดุ รูปเอกสาร และไฟล์ที่อาจมีข้อมูลอ่อนไหว
- [ ] ประวัติอาชญากรรม ข้อมูลสุขภาพ หรือข้อมูลชีวภาพ หากมีการเก็บ
- [ ] แชทระหว่างลูกค้า ร้านค้า และไรเดอร์
- [ ] Token, API Key, Firebase Admin Credential และ Secret อื่น ๆ

สำหรับแต่ละประเภทต้องระบุผู้มีสิทธิ์ดู ผู้มีสิทธิ์แก้ไข ผู้มีสิทธิ์ส่งออก ระยะเวลาเก็บรักษา และวิธีลบอย่างชัดเจน

---

## 4. การสร้างและอนุมัติบัญชีทีมงาน

- [ ] ใช้อีเมลองค์กร ไม่ใช้บัญชีส่วนตัวในการเข้าระบบงาน
- [ ] บัญชีต้องผูกกับบุคคลเดียว ห้ามใช้บัญชีร่วมกัน
- [ ] เปิด MFA โดยเฉพาะบัญชีผู้ดูแลระบบ GitHub Firebase Vercel และระบบที่มีข้อมูล Production
- [ ] กำหนดผู้ขอสิทธิ์ ผู้อนุมัติ และผู้ดำเนินการให้เป็นคนละคนเมื่อทำได้
- [ ] สิทธิ์เริ่มต้นเป็น “ไม่มีสิทธิ์” และเพิ่มเฉพาะที่ได้รับอนุมัติ
- [ ] ระบุวันเริ่มต้น วันหมดอายุ และเหตุผลของสิทธิ์ทุกครั้ง
- [ ] ใช้กลุ่มหรือ Role แทนการให้สิทธิ์รายคนแบบกระจัดกระจาย
- [ ] บัญชี Admin ต้องใช้บัญชีแยกจากบัญชีทำงานทั่วไป
- [ ] ห้ามเก็บรหัสผ่านหรือ Secret ในแชท เอกสารทั่วไป หรือไฟล์ในเครื่อง
- [ ] Secret ต้องเก็บใน Secret Manager และหมุนเวียนตามรอบที่กำหนด

---

## 5. การควบคุมสิทธิ์ใน Firebase และ Production

- [ ] Firestore Security Rules ต้องปฏิเสธเป็นค่าเริ่มต้น แล้วเปิดเฉพาะเส้นทางที่จำเป็น
- [ ] ตรวจว่า Client ไม่สามารถอ่านข้อมูลผู้ใช้ทั้งหมดด้วย Query เดียว
- [ ] แยกข้อมูลสาธารณะของสถานที่ออกจากข้อมูลคำสั่งซื้อและข้อมูลส่วนบุคคล
- [ ] จำกัดการอ่านคำสั่งซื้อให้เฉพาะเจ้าของคำสั่ง ร้านค้าที่เกี่ยวข้อง ไรเดอร์ที่รับงาน และทีมที่ได้รับมอบหมาย
- [ ] จำกัดการอ่าน GPS ให้เฉพาะงานที่กำลังดำเนินการและบทบาทที่จำเป็น
- [ ] Firebase Storage ต้องมี Rules แยกตามประเภทไฟล์และเจ้าของข้อมูล
- [ ] ห้ามใช้ URL รูปเอกสารส่วนตัวแบบถาวรที่เปิดสาธารณะ
- [ ] ตรวจชนิดไฟล์ ขนาดไฟล์ และสิทธิ์ก่อนอัปโหลด
- [ ] Firebase Admin SDK ใช้เฉพาะฝั่ง Server/Backend ไม่ใส่ Credential ใน Frontend
- [ ] ปิดหรือจำกัด Firebase Test Mode ก่อน Production
- [ ] ใช้ App Check หรือกลไกป้องกันการเรียก API จากไคลเอนต์ปลอมตามความเหมาะสม
- [ ] ตรวจ Vercel Environment Variables และ GitHub Secrets ว่าไม่มีค่าเปิดเผยใน Log หรือ Preview
- [ ] จำกัดสิทธิ์ GitHub Repository และ Branch Protection ของ `main`
- [ ] Production Deploy ต้องผ่าน Pull Request หรือผู้อนุมัติอย่างน้อย 1 คน
- [ ] บัญชีบริการและ API Key ต้องแยกตาม Environment

---

## 6. การเข้าถึงชั่วคราวและเหตุฉุกเฉิน

- [ ] ใช้การให้สิทธิ์แบบชั่วคราวพร้อมวันหมดอายุ แทนการให้สิทธิ์ถาวร
- [ ] ทุกคำขอเข้าถึงข้อมูลความเสี่ยงสูงต้องมี Ticket หรือ Incident ID
- [ ] ระบุผู้ขอ เหตุผล ชุดข้อมูล ระยะเวลา และผู้อนุมัติ
- [ ] ใช้บัญชี Break-glass แยกต่างหากสำหรับเหตุฉุกเฉิน
- [ ] Break-glass ต้องแจ้งเตือนผู้ดูแลระบบทันทีเมื่อถูกใช้งาน
- [ ] ทบทวน Log หลังเหตุฉุกเฉินภายใน [24/48] ชั่วโมง
- [ ] ยกเลิกสิทธิ์ชั่วคราวทันทีเมื่อเสร็จงาน
- [ ] ห้ามใช้เหตุฉุกเฉินเป็นทางลัดสำหรับงานประจำ

---

## 7. การบันทึกและตรวจสอบย้อนหลัง

- [ ] บันทึก Login, Logout, MFA Failure และการเปลี่ยนสิทธิ์
- [ ] บันทึกการอ่าน แก้ไข ส่งออก ลบ และดาวน์โหลดข้อมูลความเสี่ยงสูง
- [ ] บันทึกผู้ใช้งาน เวลา ระบบ อุปกรณ์ IP และ Resource ที่เข้าถึงเท่าที่จำเป็น
- [ ] ป้องกันไม่ให้ผู้ดูแลลบหรือแก้ไข Log ของตนเองโดยไม่มีการตรวจสอบ
- [ ] กำหนดระยะเวลาเก็บ Log ตามความจำเป็นและข้อกำหนดทางกฎหมาย `[เติมระยะเวลา]`
- [ ] ตั้ง Alert เมื่อมีการส่งออกข้อมูลจำนวนมาก Login จากพื้นที่ผิดปกติ หรืออ่าน GPS จำนวนมาก
- [ ] ตรวจสิทธิ์และ Log อย่างน้อยรายไตรมาส
- [ ] สรุปผลการตรวจสอบและเก็บหลักฐานการแก้ไข

---

## 8. การจัดการพนักงานย้ายงานหรือพ้นสภาพ

### ก่อนเริ่มงาน

- [ ] ยืนยันตัวตนและหน้าที่ของผู้ขอสิทธิ์
- [ ] ให้ลงนามข้อตกลงรักษาความลับและนโยบายใช้งานระบบ
- [ ] อบรม PDPA การรักษาความลับ และการรายงานเหตุผิดปกติ

### เมื่อย้ายตำแหน่ง

- [ ] ยกเลิก Role เดิมก่อนเพิ่ม Role ใหม่
- [ ] ตรวจสิทธิ์ที่ตกค้างจากโครงการหรือ Ticket เดิม
- [ ] ตรวจสิทธิ์เข้าถึงข้อมูลไรเดอร์ ลูกค้า และร้านค้าว่าตรงกับหน้าที่ใหม่

### เมื่อพ้นสภาพ

- [ ] ปิดบัญชีและ Session ทั้งหมดทันทีเมื่อพ้นสภาพหรือภายในเวลาที่กำหนด
- [ ] ยกเลิก MFA Token, API Token, SSH Key, VPN, GitHub, Firebase และ Vercel Access
- [ ] หมุนเวียน Secret ที่บุคคลดังกล่าวเคยเข้าถึง หากมีความเสี่ยง
- [ ] เรียกคืนอุปกรณ์และลบข้อมูลจากเครื่องที่องค์กรควบคุม
- [ ] ตรวจสอบการดาวน์โหลดหรือส่งออกข้อมูลก่อนพ้นสภาพ
- [ ] เก็บหลักฐานการยกเลิกสิทธิ์

---

## 9. ผู้ให้บริการภายนอกและผู้รับจ้าง

- [ ] ตรวจสอบว่าผู้ให้บริการประมวลผลข้อมูลประเภทใดและอยู่ในประเทศใด
- [ ] ทำข้อตกลงการประมวลผลข้อมูลหรือเงื่อนไขรักษาความลับตามบทบาทจริง
- [ ] ให้สิทธิ์ผู้รับจ้างเฉพาะระบบและช่วงเวลาที่จำเป็น
- [ ] ห้ามใช้บัญชี Admin ของ ChauatGo ให้ผู้รับจ้างร่วมกัน
- [ ] กำหนดการแจ้งเหตุละเมิดข้อมูลและการคืน/ลบข้อมูลเมื่อสิ้นสุดสัญญา
- [ ] ทบทวนสิทธิ์ผู้ให้บริการภายนอกทุก 3 เดือน
- [ ] ยกเลิกบัญชีและ API Key ทันทีเมื่อเลิกใช้บริการ

---

## 10. การรับมือเหตุผิดปกติ

ให้ถือเป็นเหตุที่ต้องตรวจสอบทันทีเมื่อพบว่า

- [ ] พนักงานเห็นข้อมูลที่ไม่อยู่ในหน้าที่
- [ ] มีการดาวน์โหลดหรือส่งออกข้อมูลจำนวนมากผิดปกติ
- [ ] บัญชีถูกใช้จากอุปกรณ์หรือสถานที่ผิดปกติ
- [ ] Credential หรือ API Key ถูกส่งในแชทหรือ Git
- [ ] Firebase Rules เปิดข้อมูลกว้างเกินไป
- [ ] ลิงก์รูปเอกสารหรือข้อมูลส่วนตัวเปิดสาธารณะ
- [ ] มีการใช้ข้อมูลลูกค้า ไรเดอร์ หรือร้านค้าในระบบทดสอบโดยไม่มีการปกปิด

ขั้นตอนขั้นต่ำ:

1. ระงับ Token หรือบัญชีที่เสี่ยงโดยไม่ทำลายหลักฐาน
2. แจ้งผู้รับผิดชอบความปลอดภัยและข้อมูลส่วนบุคคล
3. ระบุขอบเขตข้อมูลและช่วงเวลาที่ได้รับผลกระทบ
4. เก็บ Log และหลักฐานที่เกี่ยวข้อง
5. แก้ไขช่องโหว่และหมุนเวียน Credential
6. ประเมินว่าต้องแจ้งเจ้าของข้อมูลหรือหน่วยงานกำกับหรือไม่
7. บันทึกเหตุการณ์ บทเรียน และมาตรการป้องกันไม่ให้เกิดซ้ำ

## 12. เกณฑ์พร้อมใช้งานก่อนเปิดระบบจริง

ถือว่ายังไม่พร้อม หากมีข้อใดข้อหนึ่งต่อไปนี้:

- [ ] ใช้บัญชีร่วมกัน
- [ ] ไม่มี MFA สำหรับ Admin หรือผู้เข้าถึง Production
- [ ] ไม่มีผู้อนุมัติการให้สิทธิ์
- [ ] ไม่มี Log การเข้าถึงข้อมูลสำคัญ
- [ ] พนักงานพ้นสภาพแล้วยังมีสิทธิ์
- [ ] Firebase Rules หรือ Storage เปิดเป็นสาธารณะโดยไม่จำเป็น
- [ ] ใช้ Production Data ใน Development โดยไม่ปกปิด
- [ ] ไม่รู้ว่าใครเข้าถึง GPS เอกสารไรเดอร์ หรือบัญชีธนาคารได้
- [ ] ไม่มีขั้นตอนระงับสิทธิ์และหมุนเวียน Secret เมื่อเกิดเหตุ
- [ ] ไม่มีช่องทางแจ้งเหตุหรือผู้รับผิดชอบด้านข้อมูลส่วนบุคคล
