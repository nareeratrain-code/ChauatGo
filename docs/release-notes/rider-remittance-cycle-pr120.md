# Release Notes: รอบการโอนเงินไรเดอร์และ Realtime Rider Lock

**PR:** #120  
**Branch:** `fix/rider-remittance-verification-cooldown`  
**Commit:** `b75979b` — `Align remittance cycles and rider lock enforcement`  
**สถานะ:** พร้อมสำหรับตรวจสอบและนำไป Deploy หลังผ่านขั้นตอน Merge/Release ของทีม

## ภาพรวม

ปรับปรุงระบบรอบการโอนเงินของไรเดอร์ให้คำนวณตามเวลาไทย (Asia/Bangkok) อย่างชัดเจน และทำให้การบล็อกการรับงานทำงานจากฝั่ง Server แบบ realtime มากขึ้น โดยไม่พึ่งพายอดเงินหรือสถานะที่ส่งมาจากหน้าจอไรเดอร์เพียงอย่างเดียว

การเปลี่ยนแปลงนี้แก้ปัญหาหลักที่งานเสร็จหลังเวลา 21:00 น. ถูกจัดเข้ารอบผิดวัน รวมถึงกรณีที่ไรเดอร์ปิดแอปแล้ว Scheduler ไม่พบรายการสำหรับตรวจสอบหรือบล็อกตามกำหนด

## กติกาการจัดรอบโอนใหม่

- งานที่เสร็จก่อนเวลา **21:00 น.** จะอยู่ในรอบโอนของวันที่งานเสร็จ
- งานที่เสร็จตั้งแต่เวลา **21:00 น. เป็นต้นไป** จะถูกจัดเข้า `nextDateKey` ของวันถัดไป
- ช่วงเวลา **21:00–22:00 น.** ระบบจะแจ้งเตือนให้ไรเดอร์โอนยอด แต่ยังไม่บล็อกการรับงานทันที
- ตั้งแต่เวลา **22:00 น.** หากยังไม่มียอดโอนหรือไม่มีสลิปรอตรวจ ระบบจะพักการรับงานเป็นเวลา 24 ชั่วโมง
- งานที่ถูกจัดเข้ารอบวันถัดไปจะไม่ถูกนำไปบล็อกผิดวันในรอบปัจจุบัน
- การคำนวณใช้เวลา Bangkok โดยตรง เพื่อป้องกันปัญหาข้ามวันจาก timezone ของ Server หรืออุปกรณ์ผู้ใช้

## การคำนวณยอด

ยอดที่ต้องโอนคำนวณจากค่าบริการของงานที่เสร็จสมบูรณ์ คูณด้วยส่วนแบ่งระบบ 20% โดยไม่นับงานที่มี `riderPaid === true` แล้ว

ระบบจะแยกข้อมูลเป็น:

- `amount`: ยอดของรอบปัจจุบัน
- `dateKey`: วันที่ของรอบปัจจุบัน
- `nextAmount`: ยอดของรอบถัดไป
- `nextDateKey`: วันที่ครบกำหนดของรอบถัดไป
- `jobIds` และ `nextJobIds`: รายการงานที่อยู่ในแต่ละรอบ

หากไรเดอร์โอนเกินยอดที่ต้องชำระ ระบบยังสามารถอนุมัติสลิปได้ และบันทึก `overpaidAmount` เพื่อให้แอดมินตรวจสอบต่อได้ ส่วนกรณียอดโอนต่ำกว่ายอดที่ต้องชำระ ระบบจะไม่อนุมัติสลิป

## Realtime Rider Lock

เพิ่มการตรวจสอบ lock จาก Cloud Functions ในจุดรับงานสำคัญ ได้แก่:

- `acceptDispatchOffer`
- `claimOpenJob`

ก่อนรับงาน ระบบจะคำนวณ Orders ที่เสร็จแล้วใหม่จาก Firestore และตรวจสอบสถานะต่อไปนี้:

- `onlineLockedUntil`
- `onlineLockReason`
- `remittanceVerificationUntil`

สถานะการล็อกมี 3 ลักษณะหลัก:

1. **รอชำระ:** ยังไม่ถึงเวลา 22:00 น. จึงยังรับงานได้
2. **พักรับงานเพราะค้างโอน:** ถึงเวลาล็อกแล้วและยังไม่พบสลิปที่รอตรวจ
3. **รอตรวจสอบหลังแอดมินยืนยันสลิป:** หลังตรวจสลิปผ่าน ระบบจะคง lock ต่ออีก 24 ชั่วโมงตามกติกาใน PR นี้

Lock ที่สร้างหลังเวลา 22:00 น. จะไม่ถูกล้างเพียงเพราะเปลี่ยนวัน และจะคงอยู่จนกว่าจะครบเวลาที่กำหนด

## Scheduler และการเปลี่ยนวัน

ปรับ `sweepRiderRemit` ให้ทำงานทุก 5 นาที และคำนวณรอบโอนจาก Orders ใหม่ก่อนตัดสินใจทุกครั้ง โดยไม่เชื่อข้อมูลยอดเก่าที่อยู่ใน `settlement_queue` เพียงอย่างเดียว

เมื่อ Order เปลี่ยนเป็น `done` หรือ `delivered` ระบบจะสร้างหรือเติมข้อมูลใน `settlement_queue` ให้อัตโนมัติ ทำให้ Scheduler ยังตรวจพบไรเดอร์ได้แม้ไรเดอร์จะปิดแอปอยู่

นอกจากนี้ หลังแอดมินตรวจสลิปสำเร็จ ระบบจะอัปเดตข้อมูลรอบปัจจุบันและรอบถัดไปในคิวทันที โดยไม่ต้องรอ Scheduler รอบถัดไป

## การแจ้งเตือน FCM

ระบบส่งการแจ้งเตือนตามรอบเวลาและเก็บผลลัพธ์การส่งไว้ในเอกสารไรเดอร์ เพื่อให้สามารถตรวจสอบและ retry ได้อย่างเหมาะสม:

- แจ้งเตือนก่อนช่วงล็อก
- แจ้งเตือนเมื่อระบบพักรับงาน
- แจ้งเตือนช่วงรอปลดล็อกหลังแอดมินตรวจสลิป
- Deduplication marker ผูกกับผลลัพธ์จริงของ FCM
- หากไม่มี token หรือส่งไม่สำเร็จ จะบันทึกสถานะการส่งแทนการเลื่อน marker สำเร็จผิดพลาด
- Marker แยกตาม Bangkok date เพื่อป้องกันการใช้สถานะของวันเก่าข้ามไปวันใหม่

## Rider Dashboard

หน้าไรเดอร์แสดงข้อมูลชัดเจนขึ้น ได้แก่:

- ยอดที่ต้องโอนของรอบปัจจุบัน
- ยอดและวันที่ของรอบถัดไป
- วันที่ครบกำหนดโอน
- สถานะรอตรวจสลิป
- สถานะ cooldown หลังแอดมินตรวจสลิป
- ข้อความเตือนเมื่อใกล้ถึงเวลาพักรับงาน
- ไฮไลต์สีแดงเมื่อใกล้หรือเลยกำหนด

การแนบสลิปใช้การเลือกไฟล์เท่านั้น ไม่มีปุ่มถ่ายสลิปจากกล้องในหน้าส่งยอด

## Admin Dashboard

หน้า Admin แสดงข้อมูลรอบโอนไรเดอร์ได้ละเอียดขึ้น:

- วันที่ครบกำหนดของรอบปัจจุบัน
- วันที่ครบกำหนดของรอบถัดไป
- ยอดที่ต้องตรวจและยอดรอบถัดไป
- สถานะรอตรวจสลิปหรือปฏิเสธแล้ว
- ไฮไลต์สีแดงเมื่อใกล้หรือเลยกำหนด
- ปุ่มเปิดดูสลิป ยืนยัน หรือปฏิเสธ
- ข้อความผิดพลาดกรณี Permission Denied ที่อธิบายสถานะ lock ได้เข้าใจง่าย

หลังแอดมินยืนยันสลิป ระบบจะ mark งานที่เกี่ยวข้องว่า `riderPaid` ผ่าน Transaction และตั้ง cooldown ฝั่ง Server โดยไม่เปิดให้ Client แก้ค่า lock เอง

## Security และ Data Integrity

- การสร้าง remittance ใช้ Cloud Function และ deterministic document ID ต่อไรเดอร์และวันที่
- ป้องกันการสร้างสลิป remittance ซ้ำจากหลายแท็บหรือหลายอุปกรณ์
- Financial callable ใช้ App Check แบบบังคับ
- Firestore Rules ป้องกัน Client เขียนหรือแก้เอกสาร remittance และฟิลด์ lock โดยตรง
- การตรวจสลิปของแอดมินทำผ่าน Transaction และรองรับ idempotency
- การตรวจยอดอ้างอิง Orders จาก Server ไม่ใช้ยอดที่ Client ส่งมาเป็นแหล่งความจริงหลัก
