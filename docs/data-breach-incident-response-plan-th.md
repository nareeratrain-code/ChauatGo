# แผนรับมือเหตุการณ์ข้อมูลรั่วไหล
## Data Breach Incident Response Plan สำหรับ ChauatGo

> **สถานะ:** ร่างเพื่ออนุมัติและนำไปซ้อมจริง  
> **เวอร์ชัน:** 1.0  
> **วันที่จัดทำ:** 22 ตุลาคม 2569  
> **เจ้าของแผน:** [ชื่อ/ตำแหน่ง]  
> **ช่องทางแจ้งเหตุภายใน:** [อีเมล/เบอร์โทร/ระบบ Ticket]

เอกสารนี้กำหนดขั้นตอนเมื่อเกิดหรือสงสัยว่าเกิดเหตุละเมิดข้อมูลส่วนบุคคลในระบบ ChauatGo เช่น บัญชีถูกยึด ข้อมูลถูกอ่านโดยไม่มีสิทธิ์ Firebase Rules เปิดกว้าง ไฟล์เอกสารไรเดอร์รั่วไหล GPS ถูกเปิดเผย รูปพัสดุหลุด การส่งข้อมูลผิดคน หรืออุปกรณ์/Secret สูญหาย

แผนนี้เป็นแนวทางปฏิบัติ ไม่ใช่คำวินิจฉัยทางกฎหมาย ผู้ควบคุมข้อมูลต้องประเมินข้อเท็จจริงและหน้าที่ตามกฎหมายไทยในแต่ละเหตุการณ์ โดยเฉพาะเงื่อนไขการแจ้งสำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคลและการแจ้งเจ้าของข้อมูล

---

## 1. หลักสำคัญเมื่อพบเหตุ

ให้ถือว่าเหตุเป็นจริงจนกว่าจะตรวจสอบแล้วว่าไม่ใช่เหตุละเมิด ห้ามรอให้ทราบจำนวนข้อมูลที่แน่นอนก่อนเริ่มควบคุมเหตุ และห้ามลบ Log รีเซ็ตระบบ หรือติดต่อผู้ก่อเหตุโดยไม่มีผู้รับผิดชอบเหตุการณ์กำกับ

เป้าหมายเรียงตามลำดับคือ **หยุดการรั่วไหล ลดผลกระทบ รักษาหลักฐาน ประเมินความเสี่ยง แจ้งผู้มีหน้าที่ และป้องกันการเกิดซ้ำ**

ตามมาตรา 37 ของ พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 ผู้ควบคุมข้อมูลมีหน้าที่แจ้งเหตุละเมิดต่อสำนักงานโดยไม่ชักช้าภายใน 72 ชั่วโมงนับแต่ทราบเหตุเท่าที่สามารถทำได้ เว้นแต่เหตุละเมิดนั้นไม่มีความเสี่ยงที่จะกระทบสิทธิและเสรีภาพของบุคคล การแจ้งเจ้าของข้อมูลจะพิจารณาเมื่อเหตุมีความเสี่ยงสูงตามเงื่อนไขที่เกี่ยวข้อง [1]

## 2. ตัวอย่างเหตุที่อยู่ในขอบเขตแผน

- บัญชีทีมงาน Admin, Firebase, GitHub หรือ Vercel ถูกยึด
- พนักงานเข้าถึงข้อมูลลูกค้า ร้านค้า หรือไรเดอร์เกินสิทธิ์
- Firestore หรือ Firebase Storage เปิดข้อมูลส่วนบุคคลเป็นสาธารณะ
- ข้อมูลคำสั่งซื้อ แชท GPS หรือรูปพัสดุถูกส่งให้คนผิด
- บัตรประชาชน ใบขับขี่ เอกสารร้านค้า หรือเอกสารไรเดอร์ถูกดาวน์โหลดโดยไม่ได้รับอนุญาต
- เบอร์โทรศัพท์ ที่อยู่ หรือจุดรับส่งถูกเปิดเผยเกินความจำเป็น
- API Key, Service Account, Token หรือรหัสผ่านถูกเผยแพร่ใน Git, Log หรือแชท
- มี Malware, Phishing, Ransomware หรือการเจาะระบบ
- อุปกรณ์ที่เก็บข้อมูลสูญหายหรือถูกขโมย
- ผู้ให้บริการภายนอกแจ้งว่าข้อมูลถูกเข้าถึงหรือสูญหาย
- ข้อมูลถูกแก้ไขหรือลบจนกระทบการจัดส่ง การจ่ายเงิน หรือสิทธิของเจ้าของข้อมูล

## 3. ระดับความรุนแรง

### ระดับ 1: เหตุจำกัด

ข้อมูลไม่ใช่ข้อมูลความเสี่ยงสูง ผลกระทบจำกัด ข้อมูลถูกเห็นโดยผู้มีหน้าที่ใกล้เคียง หรือแก้ไขได้ทันทีโดยมีหลักฐานว่าไม่มีการนำออกไป

ผู้รับผิดชอบทีมสามารถควบคุมเหตุและรายงานเจ้าของแผนภายใน [4] ชั่วโมง แต่ต้องบันทึกเหตุทุกครั้ง

### ระดับ 2: เหตุมีนัยสำคัญ

มีการเข้าถึงข้อมูลส่วนบุคคลโดยไม่มีสิทธิ์ มีข้อมูลลูกค้า/ร้านค้า/ไรเดอร์หลายราย มี GPS เบอร์โทรศัพท์ ที่อยู่ คำสั่งซื้อ หรือรูปพัสดุ หรือยังไม่ทราบขอบเขตที่แน่นอน

ต้องเปิด Incident และให้ผู้รับผิดชอบข้อมูลส่วนบุคคลกับ Security Lead ร่วมประเมินทันที

### ระดับ 3: เหตุวิกฤต

มีข้อมูลอ่อนไหว เอกสารยืนยันตัวตนจำนวนมาก ข้อมูลบัญชี/การเงิน GPS ละเอียดของหลายคน การยึดระบบ Production การรั่วไหลต่อสาธารณะ การโจมตีต่อเนื่อง หรือมีความเสี่ยงต่อชีวิต ความปลอดภัย ทรัพย์สิน หรือการฉ้อโกง

ต้องแต่งตั้ง Incident Commander ทันที จำกัดการสื่อสารให้ทีมที่ได้รับมอบหมาย และพิจารณาแจ้งหน่วยงานกับเจ้าของข้อมูลโดยไม่ชักช้า

## 4. โครงสร้างผู้รับผิดชอบ

### Incident Commander

ควบคุมการตัดสินใจ กำหนดลำดับงาน อนุมัติการปิดระบบ และสรุปสถานการณ์ให้ผู้บริหารทราบ

### Privacy/Data Protection Lead

ประเมินข้อมูลส่วนบุคคลและความเสี่ยง ตัดสินใจเรื่องการแจ้งสำนักงาน/เจ้าของข้อมูล จัดทำบันทึกเหตุ และประสานที่ปรึกษากฎหมาย

### Security/Technical Lead

ควบคุมระบบ เก็บหลักฐาน ระงับบัญชี หมุนเวียน Secret ตรวจ Log และแก้ช่องโหว่โดยไม่ทำลายหลักฐาน

### Operations Lead

ตรวจงานที่ได้รับผลกระทบ ประสานร้านค้า ไรเดอร์ และลูกค้า ติดตามคำสั่งซื้อที่อาจไม่ปลอดภัย และกำหนดมาตรการชั่วคราว

### Communications Lead

จัดทำข้อความแจ้งภายในและภายนอก ตอบคำถามผู้ได้รับผลกระทบ และป้องกันการเผยแพร่ข้อมูลที่เกินจำเป็น

### Legal/Management

ให้คำแนะนำด้านกฎหมาย อนุมัติการแจ้งสาธารณะ การติดต่อหน่วยงาน และการเยียวยา

รายชื่อและช่องทางติดต่อฉุกเฉินต้องกรอกไว้ในภาคผนวกก่อนเปิดระบบจริง

## 5. ขั้นตอนปฏิบัติแบบเร่งด่วน

### นาทีที่ 0–15: รับแจ้งและตั้งต้นเหตุ

1. ผู้พบเหตุหยุดการทดลองหรือการเข้าถึงที่อาจทำให้เหตุขยาย โดยไม่ลบข้อมูลหรือ Log
2. แจ้ง `[ช่องทางฉุกเฉิน]` พร้อมเวลา ผู้พบเหตุ ระบบที่เกี่ยวข้อง และสิ่งที่สังเกตได้
3. เปิด Incident ID เช่น `CG-DB-YYYYMMDD-001`
4. ระบุว่าเป็น “เหตุสงสัย” หากยังยืนยันไม่ได้ ห้ามใช้ถ้อยคำว่าไม่มีข้อมูลรั่วไหลก่อนตรวจสอบ
5. แต่งตั้ง Incident Commander และ Privacy/Data Protection Lead
6. จำกัดการสื่อสารไว้ในช่องทาง Incident ที่กำหนด

### นาทีที่ 15–60: หยุดการรั่วไหลและรักษาหลักฐาน

1. ปิดหรือจำกัดช่องทางที่รั่ว เช่น Firebase Rule, Public Storage URL, API Endpoint, Token หรือบัญชีที่ถูกยึด
2. ระงับ Session, API Key, Service Account หรือ Credential ที่เสี่ยง และบันทึกค่าก่อนเปลี่ยนเมื่อทำได้
3. ใช้บัญชีที่เชื่อถือได้และ MFA ในการแก้ระบบ
4. เก็บ Export ของ Audit Log, Access Log, Deployment Log, Error Log, Cloud Log และภาพหน้าจอที่จำเป็นแบบแก้ไขไม่ได้
5. บันทึกเวลาตามเขตเวลาเดียวกัน เช่น Asia/Bangkok
6. ห้ามแก้ไขข้อมูลต้นฉบับที่อาจเป็นหลักฐาน
7. หากมี Malware หรือการบุกรุก ให้แยกเครื่องหรือระบบออกจากเครือข่ายโดยไม่ปิดทิ้งทันที เว้นแต่จำเป็นเพื่อหยุดอันตราย

### ชั่วโมงที่ 1–4: ระบุขอบเขตเบื้องต้น

ตอบคำถามต่อไปนี้ให้ได้มากที่สุดโดยใช้ข้อเท็จจริงที่มีหลักฐาน:

- เหตุเริ่มเมื่อใด และ ChauatGo ทราบเมื่อใด
- ระบบหรือผู้ให้บริการใดได้รับผลกระทบ
- ข้อมูลประเภทใดถูกเข้าถึง คัดลอก แก้ไข หรือลบ
- มีลูกค้า ร้านค้า ไรเดอร์ หรือทีมงานกี่รายที่อาจได้รับผลกระทบ
- มีข้อมูลอ่อนไหว ข้อมูลการเงิน เอกสารยืนยันตัวตน GPS หรือข้อมูลเด็กหรือไม่
- ผู้ใดอาจเข้าถึงข้อมูล และมีการดาวน์โหลดหรือเผยแพร่ต่อหรือไม่
- เหตุยังดำเนินอยู่หรือหยุดแล้ว
- ผู้ให้บริการภายนอกมีส่วนเกี่ยวข้องหรือไม่
- มีความเสี่ยงต่อการหลอกลวง การสวมบัญชี ความปลอดภัยทางกายภาพ หรือการติดตามบุคคลหรือไม่

หากยังไม่ทราบจำนวนที่แน่นอน ให้ระบุช่วงประมาณการและปรับปรุงภายหลัง ไม่ควรเดาตัวเลขให้ดูสมบูรณ์

### ชั่วโมงที่ 4–24: ประเมินความเสี่ยงและวางมาตรการ

พิจารณาความเสี่ยงอย่างน้อย 4 ด้าน ได้แก่ ความลับของข้อมูล ความถูกต้องของข้อมูล ความพร้อมใช้งาน และความปลอดภัยของบุคคล

ให้จัดระดับความเสี่ยงโดยพิจารณาความละเอียดอ่อนของข้อมูล จำนวนเจ้าของข้อมูล ความง่ายในการระบุตัวบุคคล ผลกระทบที่อาจเกิดขึ้น การควบคุมข้อมูลของผู้ก่อเหตุ และความเป็นไปได้ที่จะนำไปใช้สร้างความเสียหาย

มาตรการลดผลกระทบอาจรวมถึงการบังคับเปลี่ยนรหัสผ่าน การเพิกถอน Token การล็อกบัญชี การซ่อนเอกสาร การหยุดระบบที่มีช่องโหว่ การแจ้งเตือนให้ระวังการหลอกลวง การจัดคนช่วยเหลือ และการประสานธนาคาร/ผู้ให้บริการที่เกี่ยวข้อง

## 6. การตัดสินใจเรื่องการแจ้งเหตุ

### 6.1 การแจ้งสำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล

Privacy/Data Protection Lead ต้องบันทึกเหตุผลว่าเหตุใดจึงต้องแจ้งหรือไม่ต้องแจ้ง หากมีความเสี่ยงต่อสิทธิและเสรีภาพของบุคคล ให้เตรียมแจ้งโดยไม่ชักช้าภายในกรอบ 72 ชั่วโมงนับแต่ทราบเหตุ ตามข้อเท็จจริงและช่องทางที่สำนักงานกำหนด

หากพ้น 72 ชั่วโมง ให้ระบุเหตุผลของความล่าช้าและส่งข้อมูลที่ตรวจสอบได้ก่อน พร้อมส่งข้อมูลเพิ่มเติมเมื่อการสอบสวนคืบหน้า ไม่ควรรอจนทราบรายละเอียดครบทุกเรื่อง

ข้อมูลขั้นต่ำที่ควรเตรียม:

- ชื่อและช่องทางติดต่อของผู้ควบคุมข้อมูลและผู้ประสานงาน
- วันและเวลาที่ทราบเหตุ วันและเวลาที่เหตุเกิดหรือช่วงเวลาที่คาดการณ์
- ลักษณะเหตุและระบบที่ได้รับผลกระทบ
- ประเภทข้อมูลส่วนบุคคลและจำนวนหรือประมาณการเจ้าของข้อมูล
- ผลกระทบหรือความเสี่ยงที่คาดว่าจะเกิด
- มาตรการที่ดำเนินการแล้วและมาตรการป้องกันเพิ่มเติม
- เหตุผลหากยังไม่สามารถระบุรายละเอียดบางส่วนได้

### 6.2 การแจ้งเจ้าของข้อมูล

หากประเมินว่าเหตุมีความเสี่ยงสูงต่อสิทธิและเสรีภาพของเจ้าของข้อมูล ให้แจ้งโดยไม่ชักช้า ใช้ภาษาที่เข้าใจง่าย และบอกสิ่งที่เจ้าของข้อมูลควรทำทันที

ข้อความควรระบุ:

- เกิดอะไรขึ้น โดยไม่เปิดเผยรายละเอียดที่จะเพิ่มความเสี่ยง
- ข้อมูลประเภทใดได้รับผลกระทบ
- ผลกระทบที่อาจเกิดขึ้น
- ChauatGo ทำอะไรไปแล้ว
- เจ้าของข้อมูลควรทำอะไร เช่น เปลี่ยนรหัสผ่าน ระวังลิงก์ปลอม ติดต่อธนาคาร หรือแจ้งเบอร์กลาง
- ช่องทางติดต่อ Incident Response/Privacy
- หากยังสอบสวนอยู่ ต้องระบุว่าเป็นข้อมูลเบื้องต้นและจะแจ้งความคืบหน้าอย่างไร

ห้ามกล่าวโทษผู้ใช้ ไรเดอร์ หรือพนักงานก่อนมีข้อเท็จจริง และห้ามส่งข้อมูลของบุคคลอื่นไปพร้อมข้อความแจ้ง

## 7. การฟื้นฟูระบบ

1. แก้ช่องโหว่ที่ทำให้เกิดเหตุและทดสอบว่าแก้ได้จริง
2. หมุนเวียน Credential ที่เกี่ยวข้องทั้งหมด รวมถึง Credential ที่อาจถูกอ่านแต่ยังไม่พบการใช้
3. ตรวจ Firebase Rules, Storage Rules, App Check, CORS, CSP, Vercel Environment Variables และ GitHub Secrets
4. ตรวจว่ามี Backdoor, Scheduled Job, Webhook หรือผู้ใช้งานแปลกปลอมหลงเหลือหรือไม่
5. กู้คืนข้อมูลจาก Backup ที่ตรวจสอบความสมบูรณ์แล้ว
6. ทดสอบ Production แบบจำกัดวงก่อนเปิดเต็มรูปแบบ
7. ตรวจ Log หลังเปิดระบบอย่างใกล้ชิดในช่วง `[24–72]` ชั่วโมง
8. แจ้งทีมบริการลูกค้า ร้านค้า และไรเดอร์เฉพาะข้อมูลที่จำเป็นต่อการช่วยเหลือ
9. ยืนยันว่าช่องทางใช้สิทธิและคำร้องเรียนยังทำงานได้

## 8. การปิดเหตุและทบทวนหลังเหตุการณ์

Incident Commander ปิดเหตุได้เมื่อควบคุมช่องโหว่แล้ว ระบุขอบเขตได้ในระดับเพียงพอ ดำเนินการแจ้งที่จำเป็นแล้ว มีมาตรการฟื้นฟู และผู้รับผิดชอบอนุมัติการปิด

ภายใน `[7–14]` วันหลังปิดเหตุ ให้จัด Post-Incident Review โดยตอบคำถามต่อไปนี้:

- เหตุเกิดจากอะไรและทำไมการควบคุมเดิมจึงไม่หยุดเหตุ
- ตรวจพบได้เร็วหรือช้าเพราะเหตุใด
- ข้อมูลใดได้รับผลกระทบจริงและข้อมูลใดไม่พบหลักฐานผลกระทบ
- การแจ้งเหตุและการประสานงานมีอุปสรรคอะไร
- ต้องปรับ Rules, Access Control, Monitoring, Training หรือสัญญาผู้ให้บริการอย่างไร
- ใครเป็นเจ้าของงานแก้ไข กำหนดเสร็จเมื่อใด และมีหลักฐานยืนยันอะไร

ห้ามลบ Incident Record หลังปิดเหตุ ให้เก็บตามระยะเวลาที่กำหนดในนโยบายและข้อกำหนดทางกฎหมาย

## 10. ข้อความแจ้งผู้ใช้เบื้องต้น

> **เรื่อง: แจ้งเหตุด้านความปลอดภัยของข้อมูล ChauatGo**
>
> เราพบเหตุการณ์ด้านความปลอดภัยที่อาจเกี่ยวข้องกับข้อมูลของท่านเมื่อวันที่ [วัน/เวลา] ขณะนี้เราควบคุมเหตุและดำเนินการตรวจสอบแล้ว ข้อมูลที่อาจได้รับผลกระทบคือ [ระบุประเภทข้อมูลโดยไม่เปิดเผยเกินจำเป็น]
>
> เราได้ดำเนินการ [เช่น ปิดช่องทางที่เกี่ยวข้อง เพิกถอนสิทธิ์ บังคับเปลี่ยนรหัสผ่าน และประสานผู้เชี่ยวชาญ] ท่านควร [ระบุการดำเนินการ เช่น เปลี่ยนรหัสผ่าน ระวังข้อความ/ลิงก์ปลอม และติดต่อธนาคารหากเกี่ยวข้องกับการชำระเงิน]
>
> หากท่านมีข้อสงสัย กรุณาติดต่อ [อีเมล/เบอร์โทร/แบบฟอร์ม] โดยอ้างอิงเลขเหตุการณ์ [Incident ID] เราจะแจ้งความคืบหน้าเพิ่มเติมเมื่อมีข้อมูลที่ยืนยันแล้ว
